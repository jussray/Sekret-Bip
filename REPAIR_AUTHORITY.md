# Se'kret Bip Repair Authority

Se'kret Bip uses the portfolio necessary-fix default with a stricter privacy/identity ceiling because the product contains teen, parent, Circle, Bridge, Bip Jr, age-assurance, consent, and private emotional-expression boundaries.

A verified defect should be repaired instead of merely reported, but no repair witness may widen who can see, link, authorize, or act on a young person's data merely to clear a blocker.

## Required identity binding

Before any consequential repair, bind the action to the exact applicable identities:

- canonical repository, branch, base/head SHA;
- environment and deployed release identity;
- Cloudflare account/project/Worker/Pages/zone/application identity when applicable;
- Supabase account, organization, project, project URL/ref, and environment when applicable;
- affected auth/Bridge/Circle/Bip Jr/parent/teen subject class without placing private user content in the receipt;
- failure fingerprint and evidence-only proof cookies;
- before state, rollback/compensation, and post-action readback.

Any movement in a load-bearing identity expires predecessor authority/proof.

Proof cookies and fingerprints are non-secret evidence markers only. They do not grant authentication, parent authority, teen consent, merge authority, deployment authority, provider authority, or permission to inspect private content.

## Source / GitHub repair authority

Trusted repository operators may:

- repair source, tests, CI/workflows, non-secret configuration, release verification, and documentation on the existing carrier;
- add/update the narrowest useful regression test;
- rerun failed GitHub jobs when rerun is diagnostically valid;
- repair stale issue/PR evidence;
- merge only when the repository's current exact-candidate merge policy independently authorizes it.

Never weaken safety, privacy, age assurance, RLS, consent, Teen-controlled Bridge authority, Parent visibility boundaries, kill switches, or failure signals to obtain green proof.

## Cloudflare runtime repair authority

A trusted provider executor may perform a bounded reversible Cloudflare repair without a second approval when all of these are true:

- exact provider/project/runtime fingerprint is verified immediately before mutation;
- the repair restores an already-approved topology or deploys an already-authorized exact release;
- no credential creation/rotation/exposure, new spend, ownership transfer, or destructive deletion is required;
- the repair does not broaden Cloudflare Access or convert a private/authenticated route into a public route beyond the existing approved product topology;
- DNS/domain ownership is not changed;
- before-state and rollback evidence are retained;
- provider readback and exact release identity are verified after mutation;
- Playwright/browser proof verifies affected public/authenticated paths where applicable.

## Supabase repair authority

A trusted Supabase executor may perform an already-reviewed exact-project forward-only repair when it is non-destructive and preserves every existing privacy/identity boundary.

Allowed examples include applying a reviewed non-destructive migration or configuration repair whose exact project fingerprint is verified, preflight succeeds, rollback/forward compensation is defined, and live post-write state is read back.

The following remain explicit founder/human authority gates and must not be auto-repaired from a failing test or provider warning:

- authentication method or session-authority changes;
- RLS/policy changes that widen data visibility or mutation rights;
- parent/teen linking, Circle, Bridge, Bip Jr, professional, or age-assurance authority changes;
- consent or retention changes that widen collection/use;
- any access to or movement of private teen/child content beyond the already-approved contract;
- destructive data/schema/storage operations;
- service-role or other credential creation/exposure/rotation/deletion.

A restrictive security repair that reduces access may be prepared automatically, but if it changes effective user/guardian authority it still requires explicit review before production application.

## Playwright / browser witness

Playwright owns observable user-path evidence. It may trigger/reopen the matching repair incident and must verify UI/runtime fixes. Browser cookies/session state never become mutation authority.

For Se'kret Bip, relevant UI/runtime fixes are not complete without the applicable real-path Playwright evidence, including mobile where the product path is mobile-facing.

## Record witnesses

Linear/Asana may repair tracker status, blockers, acceptance criteria, evidence links, owners, and next gates. Notion/Drive/repository docs may repair stale requirements/runbooks/decision records. Slack/internal communication may repair incident/status records. Gmail may provide external consequence evidence.

Those record systems do not gain teen-data, source, deployment, database, merge, publication, or provider authority from being witnesses.

## Kill switches

Any active global, project, provider, capability, privacy, or operation-specific kill switch immediately suspends the corresponding delegated repair authority until the authorized owner clears it with current evidence.

## Hard gates

Keep explicit founder/human authority for new spending/billing, contracts/legal commitments, secrets operations, ownership transfer, destructive/irreversible actions, external publication/communication outside an approved automation, new authority expansion, and every privacy/identity/access expansion listed above.
