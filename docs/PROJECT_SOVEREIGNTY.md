# Project Sovereignty Contract

This project must preserve its core product meaning and critical operating capability if an external provider, API, SDK, model, connector, runtime, sibling project, or vendor disappears or materially changes.

## Invariants

- **Human authority comes first.** Authorized humans are the root of consequential authority. Models, agents, providers, workflows, evidence, learned knowledge, fingerprints, proof cookies, and automations may inform or constrain a proposal but may not manufacture, renew, widen, or replay authority.
- Human authority does not rewrite reality. Approval can authorize an action; only evidence can support a truthful execution or outcome claim.
- Project-owned contracts define canonical inputs, outputs, errors, authority, state, evidence, and completion semantics.
- External providers and sibling projects are adapters/capabilities, not project identity.
- Critical dependencies are classified `REPLACEABLE`, `DEGRADED_FALLBACK`, `HARD_DEPENDENCY`, or `UNKNOWN`.
- A critical capability must have an alternate adapter, local/open implementation, deterministic fallback, export/manual recovery path, or honest safe degraded mode unless a documented hard dependency is explicitly accepted.
- Critical data keeps project-owned semantics and a migration/export path; vendor IDs are provenance, not canonical identity.
- Provider swaps must not broaden authority, replay stale approvals, duplicate mutations, or weaken evidence requirements.
- Provider-specific results map into project-owned receipts; provider acceptance is not founder-goal outcome proof.
- When operated through Founder Control Room, this project remains a sovereign subsystem, not a separate founder operating system. FCR remains the founder-facing orchestration, authority, evidence, outcome, and next-gate plane.

## World as experience and knowledge

Legitimate real-world interaction may become evidence-bearing experience: user reports, runtime behavior, provider responses, experiments, analytics, deployments, repository history, operational failures, documents, and verified outcomes.

Use this learning boundary:

```text
World → observation → provenance → evidence classification → experience receipt → knowledge candidate → contradiction / red-team check → context + confidence + freshness → working knowledge → proposal → authorized action when applicable → outcome evidence → new experience
```

Experience is not automatically truth. One observation is not automatically a rule. Working knowledge must remain challengeable, provenance-backed, scoped, freshness-aware, and supersedable. Keep observation, inference, knowledge, authority, execution, and outcome separate.

## Bip-specific human-first boundary

Se’kret Bip serves children, teens, and families. World-derived learning must never become covert surveillance, manipulation, consent substitution, unsafe profiling, or authority over a young person. Privacy, dignity, age-appropriate safety, guardian/consent boundaries where applicable, auth/RLS, and the product’s existing safety contracts remain stronger than this portable sovereignty rule.

## Mandatory audit questions

> If every named provider or sibling project disappeared now, what exactly would stop, what would survive, what is the recovery path, and what evidence proves that answer?

> What experience is this system learning from, what is its provenance, what would falsify the current conclusion, and who actually holds authority for the next consequential action?

Architecture docs are not failover or learning proof. Verify contract, adapter, focused test, runtime, data-exit path, privacy/safety boundary, authority, and real-path evidence separately.

Future provider or knowledge-system work must follow the smallest reversible repair workflow: Reality → ULTRATHINK → Red Team 1 → Lindy → L99 → OODA → implement → focused proof → Red Team 2 / provider-loss + knowledge-corruption attack → Documentation Truth → rollback → next gate.
